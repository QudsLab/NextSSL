# NextSSL Rebuild Plan

Status: draft for owner review · Branch: `main` (the whole main is remade) · Started 2026-11-07

This replaces the old architecture. The old C code was removed from the tree and survives only in git history (commit `e526243`).

**Owner decisions (2026-11-07):**
- Rust is mandatory and is the safe outer layer.
- Scope is core cryptography only, not programming or infrastructure items.
- Licensing is recorded but never blocks an algorithm.
- tinyssl is decided later; nextssl comes first.

---

## 0. Non-negotiable rules

1. **Never hand-write crypto.** Every primitive is copied verbatim from a named upstream source (C or Rust) at a pinned commit, with its license file kept. Only glue code (the adapter to our interface) is ours.
2. **Every algorithm ships with Known Answer Tests (KAT).** An algorithm without passing KATs cannot leave `status = "importing"`.
3. **Nothing fails silently.** Every length, size and parameter is validated. A wrong key size returns an error, never a quiet fallback. This rule exists because of real legacy bugs: `(void)key_len` in AES, and 2016-byte truncation in the Argon2 seed engine.
4. **There is one source of truth per algorithm:** its own `algo.toml`. All tables, CMake lists, docs and `algo.json` are generated from these files and never edited by hand. The legacy code had 5 hand-kept tables that disagreed with each other.
5. **Safe by default, unsafe by name.** Broken or legacy algorithms are reachable only through the `root` namespace.
6. **Highest safety beats speed, size and convenience.**

---

## 1. Language and build: Rust shell, verified cores inside

The goal is to be fast and memory-safe, and safe even against fuzzing or injection from untrusted input.

**Layer 1: Rust safe shell (mandatory, ours).**
- Covers the public API, the envelope parser and encoder, parameter and length validation, the registry, the RNG front-end, key zeroization (`zeroize`), and the FFI boundary.
- Everything that touches untrusted input lives here: decoders, parsers, sizes.
- `#![forbid(unsafe_code)]` applies everywhere except one audited `ffi` module.

**Layer 2: algorithm cores (copied, never written by us).** Pick the source in this order:
1. Pure-Rust implementations from trusted upstreams: RustCrypto, dalek, `blake3`, `ml-kem`/`ml-dsa`, arkworks, …
2. Formally verified C: HACL\*, libcrux, fiat-crypto.
3. Reference or optimized C upstreams: PQClean, liboqs, libsodium, XKCP, BoringSSL, … These are compiled by `build.rs` with the `cc` crate and called only through a thin Rust wrapper that checks every length before the call.

**Layer 3: outward ABI.**
- The Rust crate exports a C ABI (`extern "C"`, header generated by `cbindgen`).
- The Python, PHP, Java and Swift bindings use it.
- Rust users use the crate directly, and JS uses `wasm-bindgen`.

**Tooling:**
- Build: one Cargo workspace.
- Cross-compile: `cargo-zigbuild` (Linux, Windows, macOS), `cargo-ndk` (Android), `xcframework` (iOS), `wasm-pack` / `wasm32-wasip1` (browser).
- Fuzzing: `cargo-fuzz` / AFL++ on every parser and every C-backed wrapper.
- Unsafe checks: Miri for unsafe blocks.
- Targets: the existing 29 (win 6, linux-glibc 8, musl 3, macos 3, wasm 2, android 4, ios 3).

## 2. Repository layout

```
Cargo.toml                             workspace
algos/<category>/<family>/<algo>/      one folder = one algorithm (plug in / plug out)
    algo.toml        identity, tier, params schema, upstream, license, KAT refs
    upstream/        verbatim upstream files + LICENSE (never edited; patches in patches/)
    patches/         minimal, reviewed .patch files (symbol prefixing only)
    glue.rs          adapter: upstream API -> nextssl trait for its kind (length checks here)
    build.rs         only when upstream is C: compiles upstream/ with the cc crate
    kat/             test vectors (NIST ACVP, RFC, upstream KAT, Wycheproof)
crates/
    nextssl-core/    traits per kind (Hash, Xof, Mac, Kdf, PwHash, Aead, BlockCipher,
                     StreamCipher, Mode, Kem, Sign, Kex, Drbg, Encoding, Checksum, Pow, Zk, ...),
                     typed params + schema validation, errors, zeroize, ct helpers
    nextssl-registry/  generated registry (from algo.toml), tier policy
    nextssl-rng/     OS entropy, DRBG (SP 800-90A), health tests (SP 800-90B)
    nextssl/         SAFE public API (encode, encrypt, hash, sign, kem, pqc, keygen, pow)
        envelope/    self-describing output format (section 5)
        keygen/      seed-based and password-based key generation (section 6)
    nextssl-root/    UNSAFE API: every algo, any tier, explicit params
    nextssl-ffi/     C ABI (cbindgen header) — the only crate allowed `unsafe`
    nextssl-wasm/    wasm-bindgen API for JS
    nextssl-fips/    FIPS 140-3 boundary build (approved algos only)
profiles/                              build profiles (section 4) -> cargo features
bindings/{python,js,php,rust,java,swift}
tools/
    gen/             algo.toml -> registry tables, CMake lists, algo.json, docs, badges
    import/          scaffolds a new algo folder from an upstream URL + commit
    check/           license check, layout check, symbol/prefix check
tests/
    kat/  wycheproof/  acvp/  differential/  fuzz/  ct/  sanitizers/  bindings/
docker/                                one image per test matrix row
release/                               manifest, signing, revocation
docs/reference/                        upstream source lists (catalog, repo list, source notes)
```

### Adding an algorithm
1. Run `tools/import new <category>/<family>/<algo> --upstream <url> --commit <sha>`.
2. Fill in `algo.toml` and write `glue.rs` (plus `build.rs` if the upstream is C).
3. Add the KATs.
4. Run `tools/gen`.

Nothing else is touched.

### Removing an algorithm
Delete its folder, or exclude it in a profile. Generated tables simply stop listing it.

### `algo.toml` sketch
```toml
id        = "argon2id"
kind      = "pwhash"
category  = "password-kdf"
family    = "argon2"
aliases   = ["argon2-id"]
tier      = "safe"            # safe | standard | legacy | broken | research
status    = "active"          # importing | active | deprecated | revoked
standards = ["RFC 9106"]
cose_alg  = -65601            # IANA id if one exists, else private-use (section 5)
oid       = ""
upstream  = { repo = "https://github.com/P-H-C/phc-winner-argon2", commit = "<sha>", license = "CC0-1.0 OR Apache-2.0" }
fips      = false

[params.m_kib] type="u32"   min=8   max=4194304 default=65536
[params.t]     type="u32"   min=1   max=1024    default=3
[params.p]     type="u32"   min=1   max=255     default=1
[params.salt]  type="bytes" min=16  max=64      required=true

[kat]
files = ["kat/rfc9106.json"]
```

## 3. Tiers and namespaces

| Tier | Meaning | Safe API | `root` |
|---|---|---|---|
| `safe` | current best practice, PQC first | ✅ default candidates | ✅ |
| `standard` | standardised and still sound (AES-GCM, ECDSA P-256, RSA-PSS…) | ✅ when named explicitly | ✅ |
| `legacy` | still needed for compatibility (SHA-1 HMAC, 3DES…) | ❌ | ✅ |
| `broken` | cryptographically broken (MD5, RC4, DES, classical ciphers) | ❌ | ✅ |
| `research` | candidates, experimental, unaudited | ❌ | ✅ (flagged) |

Public namespaces in C, mirrored in every binding:

- `nextssl_encode` / `nextssl_decode`: keyless encodings (base64, hex, bech32…)
- `nextssl_encrypt` / `nextssl_decrypt`: AEAD/hybrid, key or password
- `nextssl_hash`, `nextssl_mac`, `nextssl_kdf`, `nextssl_pwhash`
- `nextssl_sign` / `nextssl_verify`
- `nextssl_kem` / `nextssl_kex`
- `nextssl_pqc_*`: PQC-only shortcuts (`pqc.encrypt`, `pqc.sign`…)
- `nextssl_keygen_seed_*`, `nextssl_keygen_password_*`
- `nextssl_pow_*`, `nextssl_zk_*`, `nextssl_threshold_*`
- `nextssl_root_*`: everything, any tier, explicit algorithm + params

## 4. Variants (profiles)

> Owner: **nextssl first.** The tinyssl lists below are placeholders, to be decided later.

A profile is a query over `algo.toml` fields, not a hand list:

```toml
# profiles/tinyssl.toml
include = ["argon2id", "blake3", "sha3-256", "ml-kem-768", "x25519", "ml-dsa-65", "ed25519",
           "xchacha20-poly1305", "aes-256-gcm", "hkdf-sha3-256", "ctr-drbg-aes256", "base64url"]
```

| Variant | Contents |
|---|---|
| `nextssl` | every active algorithm, all tiers (unsafe ones only via `root`) |
| `nextssl-fips` | `fips = true` only; CMVP boundary |
| `tinyssl` | one best algorithm per role (above) |
| `tinyssl-comm` | KEM + AEAD + sign + KDF |
| `tinyssl-web` | tinyssl + JWT/JWS/COSE + PEM + HPKE |
| `tinyssl-hash` | hashes, password hashing, KDF, encodings |
| `tinyssl-pow` | hashes + PoW engine |

**Upgrade path:** a `tinyssl` build can ask to load a full `nextssl` module at runtime. This happens only with explicit user consent and only from a verified release (section 8).

## 5. Self-describing output (envelope)

The format follows existing standards, so the output is interoperable and auditable:

| Output | Standard |
|---|---|
| Encrypted data | **COSE_Encrypt0 / COSE_Encrypt** (RFC 9052/9053, IANA algorithm registry), CBOR-encoded |
| Signatures | **COSE_Sign1** |
| Password hashes | **PHC string format** (`$argon2id$v=19$m=…,t=…,p=…$salt$hash`); extends the legacy `$nss$1$` idea |
| Keys | **PKCS#8 / SPKI** (DER/PEM) with NIST/IETF OIDs (ML-KEM/ML-DSA OIDs per IETF LAMPS) |
| Text form of COSE | `nxs1.` + base64url(CBOR) |

- Algorithms with no IANA id get a stable id from the COSE private-use range, recorded in `algo.toml`.
- **Decode** reads the header and looks up the algorithm id. Decoding is refused unless the algorithm's tier is allowed by the active policy, and the default policy is `safe` + `standard`. Decoding a `legacy`/`broken` envelope requires the `root` API.
- No guessing, no `alg=none`, no downgrade.

## 6. Key generation (two engines, open-ended)

1. **Seed engine** (deterministic, fast).
   - Seed → any registered `hash`/`xof`/`kdf` → expander → key or keypair.
   - Default expander is HKDF (SP 800-56C) or SHAKE256.
   - Algorithms with native seed keygen use it directly: ML-KEM `d‖z` per FIPS 203, ML-DSA `ξ` per FIPS 204, Ed25519 seed.
   - Counter and length are always encoded with fixed width, so no truncation is possible.
2. **Password engine** (slow, memory-hard).
   - Any registered `pwhash`/`kdf`: Argon2id/i/d, scrypt, bcrypt-pbkdf, Balloon, PBKDF2, Lyra2, yescrypt…
   - Params are passed as a typed key/value map and checked against that algorithm's `[params]` schema.
   - The params are written into the envelope, so a key can always be re-derived.
- Both engines accept **any** current or future algorithm of the right kind. Nothing is hard-coded.
- Non-cryptographic sources (CRC, xxhash, Fletcher…) are accepted only through `root`.
- **PoW** uses the same hash/pwhash registry. Challenges carry the full algorithm and params, which fixes the legacy bug where Argon2 params were dropped from the wire format.

## 7. Safety engineering

- Constant-time is verified with dudect, ctgrind (valgrind taint) and `ct-verif` where possible.
- Zeroization uses `secure_zero` on every secret on every exit path; locked memory is used for long-lived keys.
- Symbols:
  - Every exported C ABI symbol starts with `nextssl_`.
  - Symbols from C upstreams are renamed with a `nextssl__<algo>__` prefix through patches/`#define`s, so two upstreams never collide.
  - A symbol-check tool fails the build on any export that breaks this rule.
- Memory safety: no `unsafe` outside `nextssl-ffi` and the per-algo C wrappers. Each `unsafe` block carries a `// SAFETY:` justification and is covered by Miri and fuzzing.
- Injection and fuzzing resistance:
  - Every external input is parsed by Rust with explicit size limits before it reaches any core.
  - Envelopes have a max size and a max nesting depth.
  - Params are typed and range-checked against `algo.toml`.
- RNG:
  - OS entropy is used with SP 800-90B health tests.
  - Test overrides exist only in `NEXTSSL_TESTING` builds and never ship. The legacy UDBF override could replace the OS RNG at runtime.
- FIPS-style behaviour inside the `fips` module:
  - Power-on self tests run.
  - Each algorithm runs a CAST before first use.
  - Any failure moves the module to an error state.

## 8. Releases, downloads and revocation

- Releases are cut only on signed tags `v*`, by GitHub Actions.
- Every artifact is listed in `manifest.json` with its SHA-256/SHA3-256, size, profile and target.
- The manifest is signed twice, with Ed25519 (minisign) and ML-DSA-65. Sigstore build provenance (SLSA) is attached.
- `revocations.json` is signed with the same keys and lists bad versions and algorithms with a reason.
- The runtime loader:
  1. Downloads only from the official GitHub releases URL, which is pinned in the binary.
  2. Verifies both signatures with the embedded public keys.
  3. Checks the revocation list.
  4. Refuses anything revoked and **falls back to the newest non-revoked release**.
- **"Is it really broken?" policy.** An algorithm moves to `broken`/`revoked` only on an official source:
  - NIST/IETF/national standards body notice,
  - CVE/GHSA,
  - peer-reviewed attack (IACR ePrint confirmed by follow-up or by upstream maintainers).

  The maintainer then signs the change. Rumours, blog posts and AI claims never revoke anything.

## 9. Testing (runs in Docker on the owner's machine and in CI)

| Layer | What runs |
|---|---|
| KAT | every algorithm, every vector, mandatory |
| NIST ACVP / CAVP | all FIPS-relevant algorithms (AES modes, SHA-2/3, HMAC, KDFs, DRBG, ECDSA, ML-KEM, ML-DSA, SLH-DSA) |
| Wycheproof | AEAD, ECDSA, EdDSA, ECDH, RSA, HKDF, MAC edge cases |
| Differential | same input vs OpenSSL, PyCA, liboqs, libsodium, BoringSSL in Docker; outputs must match |
| Fuzzing | libFuzzer + AFL++ on every decoder, parser and envelope path; OSS-Fuzz later |
| Sanitizers | ASan, UBSan, MSan, TSan builds of the full suite |
| Constant-time | dudect + ctgrind on secret-handling kinds |
| Cross-arch | QEMU: arm64, armv7, riscv64, ppc64le, s390x (big-endian) |
| WASM | node + headless browser run of the KAT suite |
| Bindings | the same KAT JSON driven from Python, JS, PHP, Rust, Java, Swift |
| Release | reproducible-build check, signature verify, revocation fallback test |

The conformance matrix (which algorithm passes which standard's vectors) is generated from test results and published with badges. We claim "tested against NIST ACVP vectors". We never claim "FIPS validated" without a CMVP certificate.

## 11. Scope and licensing

- **Scope:** core cryptography only. `scope_classification.csv` marks each of the 776 catalogued entries KEEP or DROP. DROP covers protocols, frameworks, hardware/TEE products, PKI infrastructure and tooling. KEEP entries go into P2. New algorithms are added whenever they qualify.
- **Licensing:**
  - Every algorithm is added whatever its license.
  - `algo.toml` records the SPDX id, and `tools/check` builds a license report.
  - Copyleft (GPL/LGPL) algorithms sit behind a `copyleft` cargo feature that is off by default, so the final license decision can be made later without moving code.
