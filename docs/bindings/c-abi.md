# NextSSL C ABI reference

Every language binding in `docs/bindings/` is a thin layer over this ABI. The header is
`crates/nextssl-ffi/include/nextssl.h`, generated by `cargo xtask gen` (cbindgen); never edit it by hand.

The ABI is **driven by the registry at run time**. An algorithm added to `algos/**/algo.toml` is
callable by name through these functions after `cargo xtask gen` and a rebuild, with no change in
`nextssl-ffi`. Discovery (`nextssl_algorithms_json`) always reports what the loaded library contains.

No claim of FIPS validation is made anywhere in this project. Algorithms may be "tested against
NIST ACVP vectors" where the algorithm's KAT files say so.

## Naming and tiers

| Entry point | Reaches |
|---|---|
| `nextssl_<op>` | algorithms of tier `safe` and `standard`, and only kinds that are not root-only |
| `nextssl_root_<op>` | every tier (`legacy`, `broken`, `research`, `unverified` too) |

A safe entry point called with an algorithm of another tier returns `NEXTSSL_ERR_TIER_NOT_ALLOWED` (3). It never
falls back to another algorithm. Calling a function of the wrong kind (a KEM name through `nextssl_hash_with`)
returns `NEXTSSL_ERR_WRONG_KIND` (2).

Root-only kinds (`pke`, `pake`, `statefulsign`, `zk`, `threshold`, `he`, `vdf`) exist **only** as `nextssl_root_*`
functions, whatever tier the algorithm declares. Handle operations (`nextssl_drbg_generate`, `_reseed`, `_free`) carry
no prefix: the tier was decided when the handle was created.

`nextssl_algorithm_info_json(name)` tells you which entry point an algorithm needs: `"safe_api": true` means
`nextssl_<op>` works, `false` means `nextssl_root_<op>`.

## Types and buffers

```c
typedef struct nextssl_in  { const uint8_t *ptr; size_t len; } nextssl_in;           /* input  */
typedef struct nextssl_out { uint8_t *ptr; size_t cap; size_t len; } nextssl_out;    /* output */
```

* **Inputs** are passed by pointer to a `nextssl_in`. `len == 0` accepts a null `ptr`. A null struct pointer, or
  `len > 0` with a null `ptr`, is `NEXTSSL_ERR_NULL_POINTER` (100). A length above `isize::MAX` is
  `NEXTSSL_ERR_INVALID_LENGTH` (8). Inputs larger than 256 MiB are rejected.
* **Outputs** are passed by pointer to a `nextssl_out` you fill in with `ptr` and `cap`.
  * Success: `len` is the number of bytes written.
  * Buffer too small: the call returns `NEXTSSL_ERR_BAD_OUTPUT_LEN` (10), **writes nothing**, and sets `len` to the
    required size. Pass `ptr = NULL, cap = 0` to ask for the size first.
  * Any other error: `len` is set to 0.
  * Calls with several outputs (key pairs, encapsulation) are all or nothing: if one buffer is too small no buffer is
    written and every `len` reports its required size.
  * Output never overlaps an input (do not pass the same memory for both).
* Strings (`alg`, `params`, `kind`) are NUL-terminated UTF-8. `params` may be NULL.
* Caller-chosen output lengths (`xof`, `kdf`, `pwhash_derive`, `rng_fill`, `drbg_generate`) must be 1 to 16 MiB.
* `size_t` is the platform word; the wasm32 module uses 32-bit `size_t`, so lengths there are limited to 4 GiB.

Rust-side secret buffers (keys copied from your input, derived keys, shared secrets, plaintext, and `bytes`
parameters such as a keyed-hash key) are zeroized on every exit path, including errors and a caught panic. **The memory you pass in and the buffers you receive are yours**:
wipe them with your language's facilities when you are done.

## Parameters

`params` is `name=value;name=value`. Names and types come from the algorithm's declared parameters, which
`nextssl_algorithm_info_json` lists under `"params"`:

* `u32`, `u64`: decimal.
* `str`, `enum`: the text (an enum value outside the declared set is an error, never a default).
* `bytes`: hex (even length).

Unknown names, duplicates, empty items and unparsable values are errors (5, 6, 7 or 9). Omitting a parameter takes
its declared default; omitting a required one is `NEXTSSL_ERR_PARAM` (4). Example: `nextssl_mac("hmac", "hash=sha512", ...)`,
`nextssl_encode_with("bech32", "hrp=bc", ...)`.

## Error codes

Every function returns `NEXTSSL_OK` (0) or one of these. `nextssl_error_message(code)` returns a static,
NUL-terminated English message (never null).

| Code | Constant | Meaning |
|---|---|---|
| 0 | `NEXTSSL_OK` | success |
| 1 | `NEXTSSL_ERR_UNKNOWN_ALGORITHM` | no algorithm with that id or alias in this build |
| 2 | `NEXTSSL_ERR_WRONG_KIND` | algorithm exists but is another kind |
| 3 | `NEXTSSL_ERR_TIER_NOT_ALLOWED` | tier not reachable through this entry point; use `nextssl_root_*` |
| 4 | `NEXTSSL_ERR_PARAM` | required parameter missing |
| 5 | `NEXTSSL_ERR_PARAM_UNKNOWN` | parameter not declared by the algorithm |
| 6 | `NEXTSSL_ERR_PARAM_TYPE` | parameter value has the wrong type |
| 7 | `NEXTSSL_ERR_PARAM_RANGE` | parameter outside its range or enum |
| 8 | `NEXTSSL_ERR_INVALID_LENGTH` | an input or requested length is not allowed (key, nonce, tag, ...) |
| 9 | `NEXTSSL_ERR_INVALID_INPUT` | malformed or non-canonical input (also: bad `params` syntax, non-UTF-8 name) |
| 10 | `NEXTSSL_ERR_BAD_OUTPUT_LEN` | output buffer too small; required size is in `out.len` |
| 11 | `NEXTSSL_ERR_BACKEND` | the algorithm's implementation failed |
| 12 | `NEXTSSL_ERR_UNSUPPORTED` | the algorithm does not provide this operation |
| 13 | `NEXTSSL_ERR_UNIMPLEMENTED` | scaffolded, not imported yet |
| 14 | `NEXTSSL_ERR_AUTHENTICATION_FAILED` | invalid tag, signature, proof, password or PKE ciphertext; no plaintext released |
| 15 | `NEXTSSL_ERR_NOT_INSTANTIATED` | DRBG used before instantiate |
| 16 | `NEXTSSL_ERR_RESEED_REQUIRED` | DRBG reseed interval reached |
| 17 | `NEXTSSL_ERR_ENTROPY_FAILURE` | entropy source failed |
| 18 | `NEXTSSL_ERR_WORK_LIMIT` | proof-of-work work limit reached |
| 19 | `NEXTSSL_ERR_KEY_EXHAUSTED` | stateful signature key has no one-time keys left |
| 20 | `NEXTSSL_ERR_PERSIST_FAILED` | key state could not be persisted |
| 21 | `NEXTSSL_ERR_PROTOCOL_ABORTED` | interactive protocol rejected a message |
| 100 | `NEXTSSL_ERR_NULL_POINTER` | null pointer argument |
| 101 | `NEXTSSL_ERR_PANIC` | a Rust panic was caught at the boundary (a bug; please report) |
| 102 | `NEXTSSL_ERR_BAD_HANDLE` | unknown or already released handle |

Verification functions (`mac_verify`, `pwhash_verify`, `verify_detached`, `pow_verify`, `stateful_verify`,
`zk_verify`, `vdf_verify`) return `NEXTSSL_OK` when valid and `NEXTSSL_ERR_AUTHENTICATION_FAILED` when the
input is well formed but invalid. Any other code means malformed input. Treat every non-zero code as "reject".

No panic crosses the ABI: every call runs under `catch_unwind` and a panic becomes code 101.

## Functions by kind

`[root]` marks functions that exist only as `nextssl_root_*`. Argument order: `alg, params, inputs..., sizes...,
outputs...`. All other `nextssl_` / `nextssl_root_` pairs have identical signatures.

| Kind | Functions (without prefix) |
|---|---|
| hash | `hash_with(alg, params, data, out)`; also the older `nextssl_hash(alg, data, len, out, cap, out_len)` |
| xof | `xof(alg, params, data, want, out)` |
| checksum | `checksum(alg, params, data, out)` (big-endian unless the standard says otherwise) |
| encoding | `encode_with`, `decode_with(alg, params, data, out)` (strict decode); older `encode`, `decode` |
| mac | `mac(alg, params, key, data, tag_len, out)` (`tag_len` 0 = longest declared tag), `mac_verify(alg, params, key, data, tag)` |
| kdf | `kdf(alg, params, ikm, salt, info, want, out)` |
| pwhash | `pwhash(alg, params, password, out)` (PHC string, fresh 16-byte salt from OS entropy), `pwhash_salted(..., salt, out)`, `pwhash_verify(alg, params, password, phc)`, `pwhash_derive(..., salt, want, out)` |
| aead | `aead_seal(alg, params, key, nonce, aad, pt, out)` writes `ct || tag`; `aead_open(..., ct, out)` |
| blockcipher | `blockcipher_encrypt`, `blockcipher_decrypt(alg, params, key, block, out)` (exactly one block) |
| streamcipher | `stream_apply(alg, params, key, nonce, data, out)` (same call encrypts and decrypts) |
| blockmode | `blockmode_encrypt`, `blockmode_decrypt(alg, params, key, nonce, data, out)` |
| mode | `mode_encrypt`, `mode_decrypt(alg, params, cipher, cipher_params, key, iv, data, out)` (generic mode over a block cipher) |
| kem | `kem_keygen(alg, params, pk, sk)`, `kem_encaps(alg, params, pk, ct, ss)`, `kem_decaps(alg, params, sk, ct, ss)` |
| kex | `kex_keygen(alg, params, pk, sk)`, `kex_agree(alg, params, sk, peer_pk, ss)` |
| sign | `sign_keygen(alg, params, pk, sk)`, `sign_detached(alg, params, sk, msg, ctx, sig)`, `verify_detached(alg, params, pk, msg, ctx, sig)` |
| rng | `rng_fill(alg, params, want, out)` (for example `os-entropy`) |
| drbg | `drbg_new(alg, params, entropy, nonce, personalization, &handle)`, `nextssl_drbg_generate(handle, additional, want, out)`, `nextssl_drbg_reseed(handle, entropy, additional)`, `nextssl_drbg_free(handle)` |
| pow | `pow_solve(alg, params, challenge, difficulty, max_work, out)`, `pow_verify(alg, params, challenge, solution, difficulty)` |
| pke [root] | `root_pke_keygen`, `root_pke_encrypt(alg, params, pk, pt, label, out)`, `root_pke_decrypt(alg, params, sk, ct, label, out)` |
| statefulsign [root] | `root_stateful_keygen(alg, params, pk, state)`, `root_stateful_sign(alg, params, state, msg, sig, new_state)`, `root_stateful_verify`, `root_stateful_remaining(alg, params, state, &remaining, &max)` |
| pake [root] | `root_pake_start(alg, params, role, password, context, &handle, msg)`, `root_pake_step(handle, msg_in, msg_out, ss, &done)`, `root_pake_free(handle)` |
| threshold [root] | `root_threshold_split(alg, params, secret, t, n, out)` / `root_threshold_combine(alg, params, shares, out)` (packed lists), `root_threshold_start`, `root_threshold_step`, `root_threshold_free` (interactive DKG or signing) |
| zk [root] | `root_zk_setup(alg, params, setup_params, out)`, `root_zk_prove(alg, params, setup, statement, witness, out)`, `root_zk_verify(alg, params, setup, statement, proof)` |
| vdf [root] | `root_vdf_eval(alg, params, challenge, t, output, proof)`, `root_vdf_verify(alg, params, challenge, t, output, proof)` |
| he [root] | `root_he_keygen(alg, params, he_params, sk, pk, evk)`, `root_he_encrypt`, `root_he_decrypt`, `root_he_eval(alg, params, op, cts, evk, out)` |

Envelope functions from the first ABI revision are unchanged: `nextssl_encrypt_with_key`, `nextssl_decrypt`,
`nextssl_sign`, `nextssl_verify` (COSE_Encrypt0 and COSE_Sign1 with the two default algorithms of each).

Helpers: `nextssl_version()`, `nextssl_abi_version()` (currently 1), `nextssl_error_message(code)`,
`nextssl_algorithms_json(kind, out)`, `nextssl_algorithm_info_json(alg, out)`, `nextssl_buf_alloc(size)` /
`nextssl_buf_free(ptr, size)` (library-owned memory for WebAssembly hosts; free wipes the bytes).

### Key generation and entropy

Key pairs, encapsulation, signing randomness, salts and PKE randomness come only from the audited OS entropy
source `os-entropy` (the same one the Rust safe API uses). The ABI has no RNG of its own. Deterministic variants
(keygen from a seed, encapsulation from coins) are **not** exposed through the C ABI; they exist in the Rust traits
for KAT work.

### Handles

`u64` ids, never reused, never pointers. A stale, forged or already freed id is `NEXTSSL_ERR_BAD_HANDLE`. At most 4096
handles are live at once. A handle belongs to its kind: using a DRBG id on `pake_step` is `BAD_HANDLE` and leaves it intact.

* **PAKE / threshold sessions** advance by *consuming* the state. `pake_step` and `threshold_step` are one-way: after
  any error, including `BAD_OUTPUT_LEN` (the step ran but its message did not fit), the handle is gone. Use buffers of
  at least 64 KiB for both outputs. `*done` becomes 1 on the last step; the shared secret (or key share or signature) is
  then in the second output and the handle is closed. `root_pake_free` releases an unfinished session (it also works
  for threshold sessions). `role` is 0 = initiator / client, 1 = responder / server.
* **Stateful signatures** are stateless on the wire: `stateful_sign` takes the serialized key state and returns the
  signature **and the advanced state**. Store `new_state` durably and discard the old state before you release the
  signature. Signing twice from the same old state reuses a one-time key and breaks the scheme.

### Packed lists

Share lists (threshold) and ciphertext operand lists (`he_eval`) are `u32` little-endian length followed by the item,
repeated. A truncated or oversized record is `NEXTSSL_ERR_INVALID_INPUT`.

## Discovery JSON

`nextssl_algorithms_json(NULL or "" or "<kind>", out)` returns `{"abi_version":1,"algorithms":[...]}`.
`nextssl_algorithm_info_json(name, out)` returns one object. Fields: `id`, `kind`, `category`, `family`, `aliases`,
`tier`, `status`, `standards`, `license` (SPDX), `copyleft`, `c_backed`, `safe_api`, `root_only_kind`, `cose_alg`, `oid`,
`sizes` (`{"key":{"min":16,"max":32},...}` for the fields the kind declares), `params` (name, type, required, default,
min/max or enum `values`) and `ops` (the C functions for the kind, without prefix). The `fips` flag from the registry
is deliberately not exported.

Kind names: `hash xof mac kdf pwhash aead blockcipher streamcipher mode blockmode kem kex sign rng drbg encoding
checksum pow zk threshold vdf pke pake statefulsign he`.

## What the ABI does not do

* No incremental (streaming) hashing or encryption: every call is one-shot (the underlying traits are one-shot).
* No deterministic key generation or encapsulation from a seed or coins.
* KDF extract/expand are not split (`kdf` derives in one call).
* Composed algorithms from the composition engine (`hmac(sha3-256)`, `ctr-drbg(aes-256)`, FF70 frames, `random_key`)
  are Rust-only for now; use `params` (for example `hash=sha3-256`) for registry algorithms that take one.
* Kinds with no algorithm registered today (`mode`, `pow`, `vdf`, `he`) have their C functions and unit tests of the
  pointer handling, but no end-to-end run against a real algorithm yet.
* `zk` needs scheme-specific statement and witness encodings; the ABI passes them through untouched (for the one
  registered scheme, bulletproofs, the statement is a Pedersen commitment computed outside this library).

## Building

```
cargo build -p nextssl-ffi --release                      # 367 algorithms: no copyleft, no heavy dependencies
cargo build -p nextssl-ffi --release --features everything   # all 386 (adds copyleft and the heavy algorithms)
```

Features: `copyleft` (GPL/LGPL algorithms), `bulletproofs`, `hbs-lms`, `hpke`, `opaque-ke`, `rsa`, `all-heavy`
(the heavy ones are generated into `crates/nextssl-ffi/Cargo.toml` by `cargo xtask gen`), `everything` (both). The
build produces `libnextssl_ffi.so` (Linux), `libnextssl_ffi.dylib` (macOS), `nextssl_ffi.dll` + import library
(Windows), and a static library, in `target/<profile>/`. A WebAssembly build is in [js.md](js.md).

`cargo xtask check-symbols` (run it in Docker with `NEXTSSL_SYMBOLS=1`) verifies that every symbol the cdylib exports
starts with `nextssl_` and that every function in `nextssl.h` is really exported.
